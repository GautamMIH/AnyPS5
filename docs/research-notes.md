# Research notes

Issues that needed research, with a short answer. Check here before researching; add an entry after.

## Memory

- **PS5 map flags / protection bits.** FIXED 0x10, NO_OVERWRITE 0x80, NO_COALESCE 0x400000; Kyty also accepts 0x400, 0x8000 and alignment `1 << (flags >> 24)`. Prot: CPU R 0x1, W 0x2, X 0x4, GPU R 0x10, W 0x20; write implies read; 0x40/0x80 are AMPR/ACP device bits (no host effect). CPU exec on direct/flexible maps → EACCES. (shadPS4 core/memory.h, Kyty kernel/memory.cpp)
- **Fixed map / reserve / unmap semantics.** Reserve = unbacked area, honours FIXED and address hints. Fixed map without NO_OVERWRITE replaces anything in range; with it, any overlap (reserved included) → ENOMEM. Unmap skips free parts, reserved parts become free. Protect on reserved changes metadata only. (shadPS4 memory.cpp MapMemory/UnmapMemory/Protect)
- **Direct memory is physical.** Mappings are views of a physical range: aliases share contents, contents survive unmap/remap; ReleaseDirectMemory unmaps every view. Flexible unmap zeroes. (shadPS4 memory.cpp, Kyty "anonymous fallbacks break aliasing")
- **Contiguous memory spans mappings.** Games treat adjacent mappings as one object; lookups must join pieces across allocations.
- **Single source of truth.** Registry and backing drift when updated separately; use one VA map (types: free, reserved, direct+phys offset, flexible, heap, image) that drives the backing. (shadPS4 vma_map) Implemented in GuestMemoryBacking: area map + memfd segments (one shared physical segment for direct memory), views mapped into claimed ranges.

## GPU access to guest memory

- **Shaders reading guest memory by address.** shadPS4/Kyty keep a persistent GPU mirror (sparse 4 GiB arenas or per-range buffers) + page table of device addresses; upload only CPU-dirty pages before submit (write-protect tracking); missing pages read 0 and set a fault bit, made resident next frame. Read source bytes through the unprotected backing alias. (shadPS4 buffer_cache, page_manager; Kyty bufferCache)
- **Zero-copy guest memory (tested on this machine).** VK_EXT_external_memory_host imports memfd-backed MAP_SHARED mappings (segment aliases) on Intel, NVIDIA and llvmpipe (alignment 0x1000); GPU writes are visible through other views of the segment. NVIDIA pins the whole range at import (RSS += size) and offers host-visible+coherent (uncached) types only, so import on demand in chunks, never whole segments.
- **GuestGpuMemory (implemented).** Guest ranges translate to (segment, offset) via GuestVirtualTranslate; the segment alias is imported in 32 MiB chunks (spans for crossing ranges), kept until the segment dies (Collect at WaitIdle). Descriptors and BDA ranges use the imports; no per-draw copies or write-back. Smurfs: 2950 → 1320 ms/frame. Main image / cross-segment ranges fall back to copies. ANYPS5_GPU_MEMORY_COPY=1 forces the old path.
- **Storage-buffer offset alignment.** Bind at aligned-down offset, pass remainder to the shader. (shadPS4 vk_rasterizer.cpp)

## Geometry / NGG

- **Split GS halves (GsFront/GsBack).** Fuse into one mesh program: replace the front's final `s_setpc` with the back code. (Kyty ShaderRecompiler.cpp DecodeFusedProgram)
- **Merged-stage SGPRs.** User SGPRs start at s8; s0–s7 system (s3 merged_wave_info: ES verts bits 0–7, GS prims 8–15); v5 vertex id, v8 instance id. (Mesa radv_shader_args.c)
- **Mesh draw parameters.** Six push dwords: count, base/first vertex, first instance, index size (0 = none), index address lo/hi; indices read in-shader by address. (Kyty renderDraw.cpp)
- **Layer from vertex.** Misc export: layer bits 0–10, viewport 16–19; mesh writes it per primitive from the provoking vertex. Pixel ancillary VGPR: layer bits 16–28, sample 8–11. (Kyty spirvEmitterMesh.cpp, Mesa)
- **Volume render targets.** CB_COLOR_VIEW SLICE_MAX may exceed ATTRIB3 depth; clamp to depth − 1. (Kyty colorRenderTarget.cpp)

## Indirect draws

- **SET_BASE / indirect args.** SET_BASE index 1, header bit 1 = shader type (0 draw base, 1 dispatch base). Records: auto {count, instances, start vertex, start instance}; indexed {count, instances, start index, base vertex, start instance}. (Kyty CpOpSetBase, graphicsRun.cpp)
- **Patch SGPRs.** DW2 bits 0–15 base-vertex SGPR, bits 16–31 start-index SGPR (indexed, enabled by DW3 bit 27); DW3 bits 0–15 start-instance SGPR; 0x280 = none. The CP writes the values there and the vertex shader adds them itself. MULTI: DW4 bits 0–15 draw-index SGPR (bit 31 enables), bit 30 = count from memory (min with max count); indexed count clamps to INDEX_BUFFER_SIZE. (Kyty agc.cpp decode_indirect_modifier_patch_offsets)

## System services

- **Initial user login.** Some games track players only through sceUserServiceGetEvent; the boot user must arrive as one Login (type 0) event. (shadPS4 UserManager::LoginUser)
- **Save data mount points.** Mount points are short guest paths `/savedataN` (16-byte field) served from the save directory, not host paths. (shadPS4 savedata)
- **Offline NP.** Online/NP ids return SIGNED_OUT 0x80550006; bad args 0x80550003. Trophy bad args return 0x80551604 instead of failing. (shadPS4 np_manager.cpp, np_trophy.cpp)

## Command buffers

- **Conditional branch (CbBranch).** INDIRECT_BUFFER with 14 dwords: mode (1 then-only, 2 then/else), compare function (WAIT_REG_MEM codes) on 64-bit (*addr & mask) vs reference; target runs as a chain (no return). Writer drops low address bits (compare 31:3, buffers 31:2) instead of rejecting. Flips in branch targets are reserved when reached. (Kyty CpOpBranch, AgcCbBranch)

## Textures

- **Texture cache cost (measured on Smurfs).** Full-content validation (memcmp against the snapshot) is cheap: ~19 ms/frame for 341 MB. The real cost was eviction thrash: a 256 MB budget counting snapshot + GPU copy holds ~15 large textures, so a ~25-texture working set missed every frame (218 MB re-read and re-detiled). Budget 1 GiB / 1024 entries: misses ~1/frame. Write-tracked validation would need page-level watches that coexist with render-target watches on shared pages; not worth it for ~20 ms.
- **Shader shape vs descriptor type.** The instruction's dimension picks the view (shadPS4 ImageViewInfo uses the shader's is_array): a 2D sample of an array/cube views the base layer; an array sample of a 2D texture views it as one layer. The descriptor type still defines the memory layout.

- **Storage images (image_store targets).** Were detiled/re-tiled per texel on the CPU around every dispatch (~370 ms/frame on Smurfs; Zorro's full-screen compute pass capped it at ~11 fps). Now on the GPU over GuestGpuMemory: detile from guest, tile back into device staging plus a byte mask (tiling an all-ones image), then a per-dword masked merge into guest. Texel-exact write-back matters: single-pass downsamplers (SPD) bind many mips in one dispatch, and tail mips share one block, so writing back whole tiledSize ranges clobbers the other mips (the CPU fallback still does). ANYPS5_CHECK_STORAGE_TILING=1 compares against the CPU tiler.

## Audio / video decode

- **libSceAudiodec codec ids / errors.** AT9 = 1, MP3 = 2, M4AAC = 3; errors 0x807F00xx (fpPS4 ps4_libsceaudiodec.pas). Ctrl = {param, bsiInfo, auInfo {size 0x18, addr, bytes}, pcmItem {size 0x18, addr, bytes}}; decode writes consumed AU bytes and PCM bytes back. Unfilled bsi (channels 0) makes games divide by zero.
- **M4AAC layouts (verified on Smurfs: 48 kHz stereo decodes).** Param 0x20: {size, wordSize (2 = float, per game's channels*4 sizing), config (1 ADTS, 2 raw — shadPS4 AJM), samplingFreqIndex, maxChannels, enableHeaac, enableNondelayOutput, interleaveOrder}. Bsi 0x14: {size, samplingFreq, channels (game indexes channel maps by channels-1), bitrate, heaac}. Raw streams carry no channel config: first element (SCE/CPE) narrows it. Decoded with system FFmpeg; shadPS4 uses fdk-aac.

- **libSceVideodec2.** Structs, errors 0x811D01xx/02xx and flow as shadPS4 videodec2 (FFmpeg H.264 codec 1 / HEVC 974921, handle = pointer, compute queue = pointer into title memory). Output NV12: luma then interleaved chroma, height aligned 16, picture info (Avc 0x78 / Hevc 0xB8) right after the frame for GetPictureInfo. Pitch must be 256-byte aligned (linear GPU row alignment, 2048 for 1920) or the title's linear texture over the frame over-reads; shadPS4 uses 64.

## Unreal Engine symptoms

- **Null store in UE shipping code** can be a deliberate fatal: e.g. `gc.EnableTimeoutOnPendingDestroyedObjectInShipping` crashes when GC waits too long for FinishDestroy — caused by very slow frames, not a missing API. Find cvar names by decoding UTF-16 strings next to the registration call.

## Fast clears / compression

- **HTILE depth fast clear.** Titles clear (reversed-Z) depth through HTILE (DB_Z_INFO.TILE_SURFACE_ENABLE, DB_HTILE_DATA_BASE 0x005/0x01e) without writing depth memory; ignoring it leaves stale depth and the depth test rejects the world (Zorro: HUD over black). Treat HTILE like CMASK: registered as cleared on first use, re-cleared by DMA fill or XOR-free compute write; a draw into a cleared target first clears depth/stencil to DB_DEPTH_CLEAR/DB_STENCIL_CLEAR. Debug: ANYPS5_IGNORE_DEPTH_TEST=1, ANYPS5_TRACE_DEPTH=1. (shadPS4 IsMetaCleared)
- **CMASK fast clear.** Register CMASK (only with FAST_CLEAR) as cleared on first use; DMA fill or XOR-free compute write to it re-clears; draw into a cleared target fills with CLEAR_WORD; eliminate pass = that fill for target 0. DCC ignored: surfaces stay uncompressed, so a DCC_DECOMPRESS pass (CB_COLOR_CONTROL MODE 6) is the same as an elimination pass (hardware writes the clear value into fast-cleared pixels and stores the rest uncompressed; upstream aa9a5c02). Both run in the colour block without a pixel shader: their targets come from CB_TARGET_MASK alone (Smurfs' DCC pass binds no pixel shader). (shadPS4 vk_rasterizer.cpp, texture_cache.h)

## Driver performance (Zorro gameplay, September 2026)

- **Linux write watch: asynchronous userfaultfd write-protect + PAGEMAP_SCAN (Linux 6.7+).** The Linux counterpart of Windows MEM_WRITE_WATCH, unprivileged with UFFD_USER_MODE_ONLY. Features WP_ASYNC | WP_UNPOPULATED | WP_HUGETLBFS_SHMEM; every guest view is registered with UFFDIO_REGISTER_MODE_WP when mapped. ioctl(pagemap, PAGEMAP_SCAN) with PM_SCAN_WP_MATCHING | PM_SCAN_CHECK_WPASYNC and category PAGE_IS_WRITTEN reports the written pages of a range and re-protects only them. It sees CPU and kernel writes (read(2)); writes through another mapping of the same memory (host alias, GPU imports, a second view) are not seen. Unregistered memory makes the scan fail, and a fresh view's pages read as written, so errors are safe. Costs: a clean 4 MiB scan ~2 us, scan + reset of 1 GiB ~0.8 ms, first write to a re-protected page ~0.25 us. It replaced soft-dirty bits (pagemap bit 55 + clear_refs, ~4 ms per 2 GiB per clear and process-wide, so one reset hid writes from every other user). The driver's WriteTracker keeps per-64-KiB block generations over the scans. Zorro gameplay went from ~390 to ~240 ms per frame, and the texture cache from 110 to 70 ms per frame.
- **CPU waits after every draw.** Every shader buffer is bound writable, so each draw's constant buffers count as pending GPU writes and the next draw's range check waited for the GPU. Accesses the GPU makes through imported memory only need a barrier (GpuAccessScope); only CPU reads wait.
- **Depth sampled as a texture.** Games sample depth planes (Depth64KB layout) many times a frame; writing the resident depth back to guest memory and re-uploading it cost ~31 ms each. Copy from the depth image on the GPU instead.
- **Destroying a pending CommandBatch drains the queue** (vkQueueWaitIdle); release GPU-filled objects after their fence.
- **Out-of-memory at exit.** SDL reports SIGTERM/SIGINT and window close as SDL_QUIT; treating it as an error aborted the process, and the core dump read every page of the guest's shared memory segments (allocating untouched ones), ~4 GB more on Zorro, which the OOM killer then hit. SDL_QUIT now exits (fflush + _Exit(0)); guest segments set /proc/self/coredump_filter to leave shared memory out (ANYPS5_FULL_COREDUMP=1 keeps it).
- **Frame timers on hot paths.** Every PerformanceTimer mark took the frame's mutex twice and looked the metric up by name in a std::map (string compares): ~1.2 us per guest range check, about 19 ms of a Zorro gameplay frame. Metrics are now keyed by string-literal address (merged by name when printed) with one lock per mark (~0.45 us). The remaining cost is steady_clock (~25 ns per read), so per-call paths (CheckRange, ResolveMemory) keep only their total. Marks crept back into those paths since. Timers are now off unless APS5_TIMERS=1: Zorro gameplay went from 2946-2998 to 3118-3119 frames in 120 s, and the heavy-frame median from 87.5 to 72 ms. Profile with APS5_TIMERS=1; the frame lines themselves come from FrameTiming and remain.
- **Guest range checks (~14k per gameplay frame).** Each check scanned every queued draw's write ranges and every resident render target. Queued writes now live in an interval index (added at Enqueue, removed after write-back at retire), color targets are looked up within the largest target's size of the address, and libc's watch check allocates nothing when no watch needs resolving. Upstream instead keeps a lock-free per-page protection table and flushes pending GPU writes only on data access; worth porting if the mapping check shows up again.
- **Texture churn.** Render targets change every frame, so their sampled copies were destroyed and recreated each frame (~2 ms each: vkFreeMemory, a new image, a new CommandBatch). They are now refreshed in place: same image, reused batch, one queue, so a leading ALL_COMMANDS barrier orders the copy after draws still sampling the old contents. Textures built from guest memory used SubmitAndWait, which stalled every miss on all queued GPU work. Their upload now runs asynchronously; its staging buffers and detiler pool are freed once the batch completes. Creation fell from ~5.7 to ~3 ms (the rest is allocations).
- **Unaligned storage buffers.** Zorro gameplay can bind a storage buffer at base % 16 == 2 (0x10b61c5e52). BufferViewMisalignment only carries dword-multiple misalignments to the shader. Other bases now get a detached buffer starting at the base: views with the same base share it, and only the bytes the GPU changed are written back, since another binding may have written the same memory. Verified by detaching every eligible buffer during Zorro gameplay.
- **Draw cache (shader captures).**
  - CaptureMemo keys a stage by its registered ShaderSnapshot (held, so its address cannot be reused), code address, request context (RecompileCacheKey::BuildContext: no code hash, no target) and user data.
  - A hit needs an unchanged mapping generation. The captured dwords are then checked with the capture's range guards in runs of adjacent dwords, and compared by value.
  - Zorro passes different user data on most draws (per-draw constant pointers), so only ~40% hit. The rest reuse the program's source and plan through CaptureResources(request, runtime, sameProgram) and walk the resources again.
  - The walk's cost was one guarded GuestMemory::Read per dword. ShaderMemory now reads the 64-byte line around a dword, clipped to neighbouring snapshots: reads fell from ~46k to ~11k per frame.
  - The write watch collects a range once per epoch. Epochs advance at submission start, satisfied memory waits, flips and every CPU write the driver makes.
  - Zorro: ~227 -> ~161 us per draw. The memo clears when the device changes (target).
- **Write watch and aliased direct memory.** The watch sees a write only in the view it went through, so direct memory mapped at two guest addresses hid writes from the other view's users. Only direct memory can alias (flexible and heap areas each own a segment). GuestWriteWatchCollect finds the other direct views of the range's physical bytes (a sorted list rebuilt when mappings change), scans them too, and reports each write at every view of its bytes; unaliased ranges scan as before. A freshly mapped or remapped view needs nothing: its pages read as written until first collected, and unregistered memory makes the scan fail ("written").
- **Persistent caches (upstream cf721a27).** The VkPipelineCache is kept in shader_cache/ beside the executable (checked against vendor, device and pipelineCacheUUID; saved every 10 s while it grows). Upstream's shader disk cache (serialized compiled variants, bb60336) was not ported: a 45 s Zorro run spends ~165 ms in 79 shader recompiles (~2 ms each), so it would save little here.
- **Upstream sync 2026-09-30 (step 3).** Ported: occlusion counters (19521c2; per-batch VkQueryPool queries once a title dumps PIXEL_PIPE_STAT, count written in the PS5 16-DB layout), wide BDA reads (the recompiler part of 29b46015) with GPU-computed V#s (21cb567, 74454ee), GLC/DLC coherence (28b09d4) and BVH ray intersection (9bb9416), the mesh push-block fix (13aecb4, adapted), AJM MP3 (028d465) on the system FFmpeg. Not taken: 33f9109 (this branch already translates NGG geometry programs to mesh shaders, 295a37bf), the rest of 29b46015 (recipes, unit shadows, bindless tables), the shader disk cache.
- **Upstream sync 2026-10-01.** Taken (cherry-picked or ported): recompiler fixes (VOPC 16-bit cmpx, v_fma_mix precision, 24-bit high products, BDA lookups not inlined, texel offsets, upstream's structurizer with route variables, which passes our early-return tests), pixel inputs at their SPI_PS_INPUT_ADDR slots with centroid pairs (cb66ec20's layout part: system inputs were written from v0 over the I/J pair), GE_INDX_OFFSET for direct indexed draws, 2D storage access to a 2D array's first layer, T# MIN_LOD via VK_EXT_image_view_min_lod, depth-format images for comparison sampling, libc locale/scan/realign, relinker hardening and --to-intel SHA/MONITORX/CLZERO lowering, MAP_FIXED reservations, PNG decoder, savedata params, network/TCP, DualSense HIDAPI and speaker audio. Fixed on the way: wide-string exports use the guest's 16-bit wchar_t (upstream's assume the host's, true on Windows only); a run-time sample offset moves the coordinates (Vulkan allows non-constant Offset on gathers only; Smurfs uses one). Not taken: the driver/CMake reorganisations, misaligned-buffer fixes for upstream's recorder (our shader data already carries the misalignment), DCC model passes (aa9a5c02, 4ce40333, f25695fa; DCC_DECOMPRESS mode 6 is now handled as an elimination pass, see Fast clears), label-wait timing fixes for its recorder (7df4ce40, a36ef52b), GS-half fusion (ours fuses already), 6a33a3d3's parameter-slot inputs, AMPR wait/counter commands (ours are stubs), the shader disk cache fix.
- **AJM codec 24 is Opus** (opus_decoder.h; KytyPS5 DecOpus = 24, REmu cites the SDK headers). Initialize {channels 1-2, sample rate 48000, mapping family 0}; Run input is packets each after a 16-bit little-endian length (verified on Smurfs: 0xfc TOC = 20 ms stereo CELT, 960 samples). Decoded with FFmpeg's opus decoder.
- **Mipmapped array color targets.** Slices are texture array layers each holding the whole mip chain: slice stride = chain size, rendered mip at its chain offset per slice (as storage images and textures already address them). Smurfs renders mip 0 of slice 1 of a 2-slice 8-mip 128x128 target.
- **Smurfs "stall" at frame ~30 was a silent GPU worker failure.** The AGC worker threw on a DCC_DECOMPRESS draw and exited; ReportFailure stored the error for the guest's next submit or flip, which never came: AgcRHI's RHI thread waits without timeout for its submission thread, which waits for the GPU interrupt of work that never ran, and the game thread waits on the render-thread fence. The usleep(0) spinning in GarbageCollection.cpp's FinishDestroy loop was a red herring (it finished; cumulative APS5_TRACE_USLEEP counts hid that). The driver now prints the first asynchronous failure. Method: APS5_TRACE_STALLS=<s> (guest waits outstanding longer than that, with guest callers), host threads named after guest threads (/proc/<pid>/task/*/comm), stack scans of the stopped process for code pointers (gdb cannot unwind guest frames), strings near eboot callers (objdump -b binary, file offset = address + 0x4000), APS5_TRACE_AGC_RELEASE=1 (submissions, RELEASE_MEM labels and interrupts as queued, written and delivered) and ANYPS5_TRACE_PM4=1 (now with NOP payloads). A submission whose traced packets stop short of its dword count marks where the worker died.
- **Clip and cull distances.** PA_CL_VS_OUT_CNTL CLIP_DIST_ENA_0-7 / CULL_DIST_ENA_0-7 (bits 0-15) use the distances exported on the CCDIST0/1 vectors (bits 22-23, distances 0-3 and 4-7); clipping comes from CLIP_DIST_ENA, not PA_CL_CLIP_CNTL.UCP_ENA (RadeonSI clears UCP_ENA when the shader writes distances). SPI_SHADER_POS_FORMAT has one 4-component export per enabled vector after POS0 (misc, CCDIST0, CCDIST1). The recompiler already wrote ClipDistance/CullDistance; the driver enables shaderClipDistance/shaderCullDistance and validation accepts them. Mesh-path (NGG with GS) distances are not done yet.
- **Vertex buffer OOB_SELECT.** V# word 3 bits 28-29: 2 (DISABLED) treats only a descriptor with zero records as out of range; other fetches read memory. Unreal binds unused streams as stride 0, 1 record, OOB_SELECT 2, fetched as 4 bytes. The other modes keep the record and byte checks.
- **ZERO colour export.** A target whose SPI_SHADER_COL_FORMAT is ZERO gets no export, so it is not written even when CB_TARGET_MASK and CB_SHADER_MASK enable it. SPI_SHADER_Z_FORMAT matters only with DB_SHADER_CONTROL.Z_EXPORT_ENABLE (Smurfs sets 32_R without it).
- **AJM resample parameters.** sceAjmBatchJobSetResampleParameters(Ex) are batch jobs recording the ratio (input per output sample) and its change per sample on the instance. Smurfs (FMOD) only sets ratio 1 (flags 0x2); other ratios are recorded but not applied (shadPS4 records them the same way).
- **Smurfs after these fixes** reaches the title screen ("Press any button"), at ~2.3 s per frame, with parts of the background missing. Runs occasionally abort right after frame 1 (a core dump as a thread starts), seen before these changes too; not investigated yet.
- **Linux entry argv.** The relinker's Linux entry stub stored a char** where EntryParams.argv[0] expects a char*; titles that print their arguments (Hellboy) read garbage. EntryParams is now {argc 1, pad 0, argv[0] = host argv[0], argv[1] = NULL} in a 0x120-byte block (shadPS4 layout with argv[33] and the entry address).
- **fopen of a missing file** returns NULL with errno (it threw). Games probe optional files: Astro Bot opens /app0/debuginfo.txt right after main.
- **Segments starting mid-page.** The console loader copies each PT_LOAD exactly; ld.so maps whole pages from the file, so a segment starting inside a page that holds an earlier segment's memory (Hellboy's patched IL2CPP module: code segments right after the data segment's BSS) mapped unrelated file bytes over it. A stray 1 in Boehm GC's zero-initialised thread table (GC_threads walk in stop-the-world) crashed every start. SeparateSharedPages gives such segments their own page (data moved to the end of the file, prefixed with what the earlier segments hold in that page); it runs after all patching. The relinker's appended block also starts in the first free page.
- **Depth clamp.** PA_CL_CLIP_CNTL ZCLIP_NEAR_DISABLE and ZCLIP_FAR_DISABLE (bits 26-27) together = Vulkan depthClampEnable (RADV sets both for it); one alone is rejected.
- **Comparison sampling of colour textures.** sample_c compares against the first channel whatever the format; Unity binds an RGBA8 sRGB placeholder where no shadow map is used. Such textures are decoded on the CPU (channel 0, sRGB to linear) into a D32 image.
- **Pixel inputs sharing a parameter with different interpolation** (SPI_PS_INPUT_CNTL.OFFSET pointing two inputs at one export, one flat and one smooth): all read the parameter per-vertex (fragment barycentric); flat ones take vertex 0 (the provoking vertex), smooth ones the barycentric weighting.
- **Crash reports list callers.** An unhandled SIGSEGV now prints up to 24 return addresses found on the faulting stack (words after a call instruction, read with process_vm_readv so the scan cannot fault), as module+address. Words from earlier calls can appear (stale frames).
- **Guest files never use descriptors 0-2.** Unity closes descriptor 0 at start (its "no file" value); the host then gave the next open() descriptor 0, later close(0) calls closed whichever file held it, and Unity's Loading.Preload thread read asset bundles through a dead or reused descriptor: short reads, garbage element counts (e.g. 0xbf6a5712) and null arrays crashed about 2 runs in 3 at random places. Host opens now move descriptors below 3 up (F_DUPFD 3) and guest closes of 0-2 leave the host streams open. Found with ANYPS5_TRACE_FILES=2 (every descriptor read, seek and close with its thread) and the crash report's thread name and registers.
- **Rect lists with per-vertex (custom) interpolation.** The generated tessellation stages already make non-flat parameters linear over the rectangle (fourth corner extrapolated), so per-vertex inputs read consistent values in either triangle; the restriction is gone.
- **Buffer ADD_TID in graphics stages.** ADD_TID adds the lane (SubgroupLocalInvocationId & 63) to the record index in any stage; validation checks subgroup support per stage.
- **Hellboy (Unity IL2CPP, PPSA11264)** reaches its title menu and the intro story with no crash in four 90 s runs (575-1333 frames).
- **Astro Bot (backport 4.xx by ManwonHp)** ships firmware system libraries in fakelib/ (Agc, AgcDriver, Ampr, PlayGo, Psml); the relinker uses AnyPS5's where it has them. Its PSML copy imports tool-memory kernel calls (sceKernelAllocate/Map/ReleaseToolMemory, sceKernelAvailableToolMemorySize), AgcDriver user-data packet calls and sceVideoOutSysAddSetModeEvent2, not yet provided. The dump in Downloads lacks 148,600 of the 166,723 files its ampr_emu.index lists (all of data/prein/sound, data/system, most levels); it stops with the engine's own file error 0x84020001 (KernelFile.cpp) opening pri_master_buss.szd.
- **Memory pools are never backed.** sceKernelMemoryPoolCommit/Decommit only change the protection of a Reserved range, which stays host PROT_NONE: a game using memory pools would fault on the committed range (found by audit; no test title hit it yet).
- **Render-target and depth transfers on the GPU (3D performance, October 2026).** Measured on Smurfs' title screen: ~39 forced write-backs of resident surfaces per frame, most from draws binding a 237 MB heap as a writable buffer (Unreal places render targets in it), each costing a full queue wait, a download, CPU tiling into guest memory, an invalidation and a CPU re-upload; depth was detiled and tiled on the CPU. With guest memory imported (GuestGpuMemory), resident colour targets and depth planes now go GPU-to-guest-memory directly: write-back tiles on the GPU and copies into the imported buffer in draw-queue order (DrawQueue::NoteGuestWrite keeps CPU accesses waiting until the batch completes; WriteTracker::NoteGpuWrite tells the texture cache), and upload copies/detiles from it. GPU consumers need no CPU wait; CPU consumers record the same GPU write-back and wait once. Depth uses the texture detiler's Depth64KB mode (TexelOffset matches DepthTargetLayout; tested) with descriptor sets prepared once per guest mapping (TextureDetiler::Prepare/Record), because the detiler's shared pools are never recycled. 16-bit depth widened to float and layered colour targets keep the CPU path. The guest memory import must exist before the caches are created (they copy the context): it was created after them, so no cache saw it. Smurfs: driver 1367 -> 954 ms/frame, 63 -> 90 frames per 90 s. APS5_TRACE_RESOLVE=1 logs each forced write-back with its access site (sites now name draw, dispatch, draw_capture, wait_reg_mem, cond_branch, pm4_execute, indirect args).
- **Next bottleneck: shaders read guest memory over PCIe.** With the CPU work gone, Smurfs is GPU-bound (~210 ms GPU busy per frame). Over the same 15 frames, draws cost ~0.86 ms of GPU time each with imported (system RAM) guest memory against ~0.39 ms with ANYPS5_GPU_MEMORY_COPY=1 (that path crashed at frame 15 there). A device-local buffer cache (VRAM copies of guest buffers, refreshed from tracked CPU writes, written back lazily; as shadPS4's buffer cache) is the next step.
- **The device-local buffer cache did not pay (October 2026, RTX 3050 6 GB laptop).** GuestGpuMemory::ResolveRead serves read-only buffer regions and vertex buffers from a device-local mirror per import. Stale 64 KiB pages are copied in queue order (vkCmdCopyBuffer from the import), and invalidated by a WriteTracker listener that hears CPU collections, NoteGpuWrite and NoteAliasWrite. The budget is a quarter of the largest device-local heap, at most 1 GiB, and only ranges up to 8 MiB are mirrored. A 3 GiB budget ran the game out of VRAM. Compared over the same frames, with no mirror against the mirror: the first 40 Smurfs frames took 112 against 163 ms GPU, and a whole 90 s run 212 against 233 ms GPU and 792 against 923 ms driver. A build that never refreshed pages, roughly the cache's best case, managed only 115 ms. In-place PCIe reads were not the bottleneck. The 0.86 against 0.39 ms comparison above came from runs that mixed scenes. The mirror stays opt-in (ANYPS5_GPU_MIRROR=1); APS5_TRACE_MIRROR=1 logs ranges it cannot watch. What dominates instead: frame 60 had 157 ms of draws and dispatches (258, ~0.6 ms each), depth texture copies 37 ms (28), texture uploads 13 ms.
- **Per-draw GPU profile (APS5_PROFILE_GPU_DRAWS=1).** Each draw and dispatch is timed on the GPU in three phases: setup (barriers, uploads, target transitions), work (render pass or dispatch) and teardown. Totals are printed per shader-and-target key every APS5_PROFILE_GPU_FRAMES (60) frames. In a Smurfs gameplay stretch, setup cost more than the work itself: 46 against 26 ms per frame. Setup is dominated by render targets being re-uploaded after an alias evicted them. Single full-screen draws spend ~5 ms in setup for 0.1 ms of work.
- **Render-target churn (APS5_TRACE_RT=1).** This logs uploads, write-backs, invalidations, replacements and the resolves that cause them. Smurfs replaces ~28 targets a frame: bloom and downsample chains reuse one allocation at several sizes (89x50 -> 178x100 -> 356x200 at the same address). Each replacement writes the old target back and uploads the new one. Watches may now share pages (GuestMemoryTracking: a shared page takes the strictest protection; tests/GuestMemory.cpp CheckSharedWatchPages), and residents are evicted only on byte overlap, not page overlap. Neither changed the count, because these targets overlap in bytes. Keeping aliased targets resident needs format and size aliasing in the render cache, which is still open.
- **The executable's own segments were copied for every draw (fixed).** Relinked games are part of the host executable. GuestAllocations registers its PT_LOAD segments (172 MiB in Smurfs: text, rodata, data and bss), and every draw leasing registered memory copied all of them on the CPU (~1.7 GB per 5000 reads, GuestMemory.Read ~107 ms per frame). The NVIDIA driver will not import them with VK_EXT_external_memory_host (out of device memory on file-backed pages), and marking image pages GPU-invisible until a GPU mprotect broke rendering. GuestGpuMemory::ResolveImage now keeps a copy per range. Read-only ranges are copied once. Writable ranges register with the userfaultfd write watch (GuestWriteWatchAddHost) and refresh only the 64 KiB blocks written; ranges that cannot be watched are recopied for each use. Smurfs: 120 -> 142 frames per 90 s, driver 715 -> 602 ms per frame, CPU copies 107 -> 16 ms. ANYPS5_NO_IMAGE_COPY=1 restores per-use copies. APS5_TRACE_READS=1 lists GuestMemory::Read callers by bytes, for addr2line.
- **Test windows (ANYPS5_BACKGROUND_WINDOW=1) are hidden.** KWin ignores SDL's no-activation hint, SDL runs through XWayland here, and minimizing is asynchronous on X11. A window reporting a 0x0 drawable at creation aborts presentation setup. The window is therefore created with SDL_WINDOW_HIDDEN: it is never mapped, the game runs and presents normally, and frame dumps work.
- **PAGEMAP_SCAN needs a page-aligned start (fixed).** An unaligned start fails with EINVAL, so CollectWrites failed for every buffer not starting on a page (most small ones). CpuWrittenSince then treated them as written, and a mirror treated them as never written: stale data that hung the GPU in Smurfs. CollectWrites now scans the range's whole pages. Host-heap ranges (libc malloc) are never watched; WriteTracker::CpuCollect reports them, and copies must not be made of them.
- **Global/flat stores write through the BDA table (fixed).** ResourceTracker set ShaderInfo::bdaWrites only for stores through GPU-selected V#s. Programs with global_store/flat_store leased registered memory read-only, so their writes went unnoted (and into a read-only copy if one is used). Address-based stores now set bdaWrites.
- **Gameplay regression test.** tools/gameplay_test.sh (GAME, SAVE env) restores a frozen save copy into a fresh relink and presses Cross into Monasterio's Hacienda (~60 s); it caught upstream's structurizer failing a gameplay shader (an early return nested in an enclosing selection), now retried with this branch's early-return rule.
- **Asynchronous GPU completion.** RELEASE_MEM (label plus EOP interrupt) and submission completion no longer idle the GPU. They queue behind a GPU marker (an empty fenced batch after the queued draws; one queue, in order) and complete in order. Completing retires the finished draws first (writing back copied buffers), then writes the label, publishes the serial and raises the interrupt, which happens outside gpuMutex. The worker drains them before packets the CPU executes, before re-checking a WAIT_REG_MEM, and at conditional branches, flips and suspends; a completer thread finishes them while the worker is idle. ACQUIRE_MEM and EVENT_WRITE cache and partial-flush events are GPU barriers. Zorro: CPU waits went from ~115 to ~27 ms per gameplay frame.
- **Autosaves steer scripted runs.** Zorro autosaves to the run folder's _sd, and the next run continues from there, so A/B runs of different builds land in different scenes. Clear _sd and _sd_backup before each run.
- **Per-queue workers would not help the test titles.** Timing the worker per queue kind: Zorro and Spirit spend ~99% of the worker's time on the graphics queue (queue 0) and none on compute queues. The worker thread is saturated by one queue, so parallelism has to come from splitting graphics-queue work (e.g. a decode/capture stage feeding a recording stage), not from one worker per queue.
- **Per-draw fixed costs.**
  - The pipeline and shader-validation keys copied each stage's SPIR-V (kilobytes) into a string per draw. They now use RecompileResult::variantId, falling back to the code when it is 0: ~19 us less per draw.
  - Every Vulkan call resolved its function by name (vkGetDeviceProcAddr). Context::Function now caches the result per resolver, device and literal name address, re-resolved after any device is destroyed (DeviceFunctionEpoch).
  - Allocating a command buffer and fence cost ~600 us on this driver, and every cached texture kept its upload batch. Destroyed batches now recycle theirs (freed before the pool goes), and finished snapshot uploads drop their batch: texture copies ~260 -> ~15 us.
- **Level-load hitches were texture creation, not shader compilation.** In Zorro's slow frames (>500 ms), texture creation took ~2.8 s and shader compilation plus pipeline creation ~0.7 s. Each texture cost ~1.6 ms, ~1 ms of it vkAllocateMemory (one allocation per image). ImageMemory now sub-allocates optimal images from 64 MiB device-local blocks (first fit, neighbours merged on free; images over 16 MiB are allocated alone). Image memory ~1017 -> ~10 us per texture; slow frames 12 (17.8 s) -> 3 (4.6 s) per 120 s run. What remains is copying the ~4 MiB snapshot into host-coherent staging memory (write-combined, ~0.65 ms) after reading it from guest memory (~0.5 ms). Detiling straight from imported guest memory would remove both.
- **Mapping snapshot misses (fixed).** CheckRange re-read /proc/self/maps (~1.3-20 ms) whenever its snapshot did not cover a range. There were two causes. Render-target watches mprotect guest pages, so snapshots taken during a watch go stale. And games probe the same unmapped descriptors every frame (e.g. 0x80400000025b). Guest memory is now answered from libc's area map (GuestVirtualAccessible: committed areas whose guest protection makes the host mapping readable or writable). Ranges that fail against a fresh snapshot fail again without a reload until the mapping generation changes. Zorro: range-check time 6.45 -> 2.42 s per 110 s run; Smurfs' uncovered reloads ~6 -> 0 per frame.
- **Frame dumps no longer depend on the window.** ANYPS5_DUMP_FRAMES dumps every Nth flipped buffer before the presentability check; a minimized window presents nothing, which silently stopped earlier dumps.
- **Compute dispatches were synchronous (~7 ms each).** Each drained the draw queue, created a shader module, pipeline layout and pipeline, submitted its own batch, waited on its fence and destroyed everything again. Dispatches now record into the draw queue with full barriers before and after: the same ordering, kept on the GPU. Resources are written back at retire like draws, and pipelines are cached by variant id plus descriptor layout key. Zorro: ~7.2 -> ~0.37 ms per dispatch. Most of the saved wait reappears at later sync points (draw-queue waits), so the GPU itself is likely a large part of the frame; GPU timestamps would tell.
- **GPU time (ANYPS5_GPU_TIMING=1).** Every CommandBatch writes timestamps at its start and end (reset in-band with vkCmdResetQueryPool). Completed batches add their duration to a per-label total, and each flip reports GPU.<label> and GPU.busy. Zorro menus: 25.7 ms frames with 17.3 ms GPU busy (draws 13.8). Heavy gameplay: 162.6 ms frames with 114.6 ms GPU busy: draws and dispatches 56, render-target copies 38.4, texture uploads and detiling 20.2. The GPU is the main limit now. Copying render targets into sampled textures costs a third of it; sampling the resident image directly (a view with MUTABLE_FORMAT, in a sampled layout) would remove the copies.
- **Depth sampled directly.** A texture over a resident depth plane that samples depth values as they are (R32 float over D32, R16 unorm over D16) is a depth-aspect view of the resident image: no copy. The target moves to SHADER_READ_ONLY_OPTIMAL in the work's upload pass, and back when it is rendered to again. Depth images are created with SAMPLED usage where the format allows it. Draws that render to the depth they sample (soft particles, screen-space effects) keep the copy, since that would be a feedback loop. Removing those needs read-only depth attachments for draws that do not write depth. Each depth copy (image -> buffer -> image, with decompressing transitions) cost ~2 ms of GPU time. Zorro: depth copies 45 -> 30 ms per heavy frame. Spirit from a cleared save: 325 -> 553 frames in 90 s. ANYPS5_NO_DIRECT_DEPTH=1 restores copies.
- **Saves skew Spirit runs too.** Spirit autosaves into its run folder like Zorro, so repeated runs of the same folder start later in the game; clear _sd before every comparison run. Spirit frame counts earlier in this work mix builds with save progress.
- **Scripted input is time-based.** As the driver gets faster, presses land in different menu states and runs diverge. Compare per-call costs or matching scenes (check dumped frames), not per-frame totals over fixed frame ranges.
- **Profiling runs.** ANYPS5_SCRIPTED_INPUT="25:cross,30:cross" reaches gameplay unattended; frames after the scene settles are the ones to compare (scenes vary 200-1000+ draws a frame).
- **Worker/device overlap is not the main lever (October 2026, Zorro gameplay ~37 ms).**
  - Per frame: the worker spends ~21 ms on the CPU, the device thread ~24.5 ms in ~1300 jobs, and the GPU is busy ~16.7 ms. execute_to_flip_packet matches the flip interval, and the game waits in sceKernelWaitEqueue about one frame ahead.
  - By default the worker drains the device thread at ~200 WAIT_REG_MEM packets a frame (~8 ms). With ANYPS5_QUEUE_WAIT_REG_MEM=1 those drains go, but frame time does not move. The worker's CPU rises ~2.4 ms, because DeviceThread::Check scans a longer job queue on every read. Its waits move to 0x9f register-pair reads (~2.4 ms), and the device thread still idles ~20% of the time.
  - So the bottleneck moves between the two threads within a frame. Even perfect overlap is bounded by device work (~27 ms). The way to 16 ms is cutting both threads' CPU per frame.
  - Smaller findings:
    - Giving the driver threads exclusive P-cores (moving every other thread to CPUs 0-3 and 8-11 externally) gained ~1-2 ms median over 2+2 runs.
    - Per-job queue overhead (locks, wakes, DirtyRanges) is ~2 ms a frame across both threads.
    - The driver cores run at ~3.7 of 4.6 GHz (93 C package).
  - Debug aids:
    - APS5_TRACE_DEVICE=1: device thread idle, job wall and job CPU time.
    - APS5_TRACE_READ_WAITS=1: worker reads that wait for the device thread, by access site and PM4 opcode, including gpuMutex waits.

- **Where 60 fps is lost (October 2026).**

  - The per-draw CPU cost spreads over shader resources (CheckRange/GuestMemory::Read ~40 ms a frame), shader memory capture (~27 ms), the texture cache (~30 ms) and waits.
  - Smurfs is GPU-heavy through PCIe: render and depth targets move ~920 MB a frame between guest memory (system RAM) and the GPU. The causes: targets replaced at an address (~14 write-backs a frame), a layered lookup volume read as a texture (~11), compute or draws reading target memory as buffers (~13), plus ~30 uploads.

- **Label waits are GPU-side drains (implemented).** The usual label pattern is: fill 0 (DMA_DATA), RELEASE_MEM writes 1 after the GPU work before it, WAIT_REG_MEM == 1. On the console the command processor waits; the CPU never stalls. The PM4 worker used to block until the GPU drained, serializing CPU recording with GPU execution (~30 ms a heavy Zorro frame).
  - A WAIT_REG_MEM is satisfied without reading memory when either holds:
    - a pending RELEASE_MEM (immediate data) writes a satisfying value to the label;
    - a WRITE_DATA or small fill recorded on the GPU, and still the label's last queued writer (DrawQueue::LastWriter serials), leaves a satisfying value.
  - It becomes a full GPU memory barrier: all GPU work runs in one queue in order. Packets the CPU executes drain pending completions first, so labels still land before them.
  - Reading the label would have waited for the batch writing it. ANYPS5_CPU_WAIT_REG_MEM=1 waits on the CPU.
- **WRITE_DATA to memory runs on the GPU** (vkCmdUpdateBuffer, up to 64 KiB), like DMA_DATA. It used to drain every queued draw (~19 ms a heavy Zorro frame). ANYPS5_CPU_DMA=1 executes both on the CPU.

  - WriteTracker now also logs each GPU write with a sequence number (GpuWrittenSince). A texture is compared again only if the GPU wrote its range since it was last read or compared; this is shadPS4's per-image dirty flag.
  - This is sound because validation first range-checks on the CPU, which waits for queued GPU writes of the range. A draw's own storage images are noted before the draw is queued, so ShaderResources re-marks overlapping textures (TextureCache::NoteDrawWrites).
  - APS5_VERIFY_TEXTURE_TRACKING=1 keeps the snapshots and compares them whenever tracking vouches for a texture: 0 mismatches in 410k checks (Smurfs, Zorro gameplay).
  - Smurfs steady state: 498/496 -> 473/477 ms a frame; compares 32 -> 1 ms. ANYPS5_STICKY_GPU_WRITES=1 restores the former rule.
- **Occlusion as "always visible" did not help Smurfs.** shadPS4's fake ZPASS counters remove ~36 full drains a frame, but over four 150 s runs Smurfs' frame time did not improve (509/538 against 506/514 ms): the time moved to other waits. Not adopted; precise counts stay.
- **Exact per-draw resource reuse did not pay (parked on wip/resource-templates).**
  - Upstream's draw templates reuse a draw's ShaderResources when every input repeats, and revalidate before use. An unbounded trace of Zorro gameplay (APS5_TRACE_TEMPLATES) suggested about 50% exact repeats, and nearly all the rest differ only in data-buffer contents and moved read-only buffers.
  - Implemented exact reuse for read-only, in-place bindings: revalidated by mapping generation, a fresh GPU-access check of each range and texture identity. APS5_VERIFY_TEMPLATES found no mismatches, but it was slower:
    - At 4096 entries, gameplay frames have so many draws that keys do not repeat before LRU eviction: 2.4% hits.
    - At 32768 entries, the held data buffers and descriptor sets drain the pools, so fresh builds stall (2+ s frames). Held textures also kept evicted texture memory alive (an out-of-memory error until templates were dropped with their textures).
  - Untried: copying the template's descriptor set and patching only the data buffers. This keeps nothing heavy alive, but the per-draw data copies remain, so the gain would mostly be the skipped texture and sampler lookups.
- **Write tracking keeps each range's last write (implemented).** Texture validation asked "written since stamp s?" by scanning logs of GPU, driver and alias writes back to s, and checked CPU writes with one hash lookup per 64 KiB block. That cost 17 ms per heavy Zorro frame (GPU check 8-11 us a call). Each kind of write now keeps an interval map of disjoint begin -> {end, stamp} entries, where a newer write replaces the parts it covers. A query visits only the intervals over its range: GPU check 0.22 us, CPU check 2.9 us (the rest is the collection syscall). The map is exact, while the bounded logs answered "written" for anything older than their window. APS5_VERIFY_TEXTURE_TRACKING found 0 missed writes in 434k (Zorro) and 130k (Smurfs) checks.
- **Graphics pipelines share render passes and dynamic state (implemented).** A Pipeline owned its render pass and a framebuffer over the target views, and baked viewport, scissor, blend constants, depth bias and bounds and stencil masks and references. Its key therefore included target identity, entries pinned their targets, and the cache was capped at 128. Spirit recreated about 200 pipelines a frame (57k in 90 s), Smurfs about 50.

  - Spirit creates fell from 57347 to 164 and its title scene from 240 to 206 ms a frame; Smurfs creates fell from 10138 to 91.
  - Still open: cold compiles (13.6 ms each on Hellboy's first run after a create-info change; about 1.5 ms warm). Asynchronous compilation that skips draws until a pipeline is ready glitches. The clean route is VK_EXT_graphics_pipeline_library: fast-link precompiled stages, then swap in an optimized pipeline compiled in the background (DXVK). It pays on first runs only, since the pipeline cache persists to disk.
  - Measured before building it (APS5_TRACE_PIPELINE_CREATES=1, Hellboy, with ANYPS5_NO_SHADER_CACHE=1 and __GL_SHADER_DISK_CACHE=0): 285 cold creates with shaders never compiled before cost 13.1 s (about 46 ms each). - **Pipelined driver (the default since 2026-10-04; ANYPS5_PIPELINED_DRIVER=0 turns it off).**
  - The worker decodes PM4 and captures shaders while a device thread records draws and GPU barriers in order, under the tracking mutex, like DXVK's command-stream thread. Every other device call drains it first.
  - The worker's guest reads do not take the tracking mutex. The libc area map got its own reader-writer lock: GuestVirtualAccessible reads it shared, and everything else in GuestMemoryBacking takes it exclusively.
  - DeviceThread::Check decides what a read needs: nothing, a resolve under the mutex, a wait for the last queued job writing the range, or a full drain. The inputs are queued jobs' targets and writable buffers, dirty resident surfaces published after each job, and GPU writes since the last idle point (VulkanDevice::WaitIdle publishes it). Write-backs at completion (copied writable buffers, storage images) count as unknown writes until the next idle point.
  - APS5_VERIFY_PIPELINE=1 checked 12.1M fast-path skips with nothing missed. APS5_TRACE_PIPELINE=1 counts why reads take the slow path.
  - Lessons: blanket "unknown" for BDA draws, all resident surfaces (instead of dirty ones) and full drains for every slow read each cancelled the overlap. Timers distort pipelined profiles, because both threads lock the frame's statistics.
  - Measured gain: none so far. In three alternating Zorro gameplay runs each (120 s), pipelined got 3297-3335 frames (median 59.5-61.8 ms) and unpipelined 3305-3368 (59.1-60.9 ms). An earlier single run of 3610 frames was an outlier. Hellboy stays bimodal either way. The heavy frames are bound by something other than the worker's CPU time; the next measurement should be the game thread and the GPU per frame.
- **Reusing repeated draws' work does not pay in Zorro.** Of 1.2M capture walks (same program, new user data), only 1% produced the resources of the program's previous capture. The user data points at different descriptor tables: heavy frames are about 1000 distinct draws, not repeats. Keying the capture memo on the user data the plan reads would hit about 1% of the time. Together with the parked exact templates, per-draw caching is exhausted; gains must come from cheaper work per draw (SRT evaluator, texture lookups, range checks) and from overlap (pipelined driver).

- **Prepared shaders: what upstream's model saves here (design, 2026-10-10).** Zorro gameplay profile (gperftools, glibc allocator; profiled ms per frame, real time ~1.7x): the worker's draw() is 9.7 ms. Capture 3.7 ms (SRT walk 2.6, captured words and memo keys 0.6), Recompile(request, capture) 2.2 ms (materializeResult 0.9, memo hash 0.55, evicting memo entries 0.54), DecodeVertexStageInfo 1.0 ms (0.86 of it guarded reads, two per vertex semantic), ShaderMemory copying the registered code and header of every stage 0.64 ms, DecodeState 0.45, BuildRectListShaders per rect-list draw 0.34, queueDraw 0.75. The registered code and header need no per-draw copy into ShaderMemory (the snapshot is immutable and held). Rect-list stages depend only on the vertex exports, fragment parameters and the highest binding: prepared per such key.

Sources whose memo lookups hit under 1 in 8 now skip the memo (no hash, insertion or eviction; 43% of materializations), and the rest hit 72%. ## Frame overlap: ceiling measured, not worth building (2026-10-12, Zorro)

- **Ceiling experiment** (unsafe, not kept). Releases completed when the device thread reaches them, and address-table stores counted as writing nothing.
  - First run: slower, 24.3 vs 22.2 ms. The GPU tail went from 3.8 to 0.25 ms, but the worker's decode grew from 16.45 to 21.4 ms with its CPU unchanged.
  - The worker was blocked on gpuMutex (~2.4 ms a frame). Its holder was `AgcCompleter`: the early label write resolved its range and waited for the GPU (`CommandBatch::Wait`) under gpuMutex, and the worker's resolves did the same.
  - The flip packet also drained the device thread once a frame (~2.1 ms with the device thread behind).
- **After fixing those** (below), the ceiling equals normal mode: 22.16 vs 22.36 ms, chain 17.3 + 3.3 + 0.9.
  - Zorro submits a frame only after the previous frame's end-of-frame interrupt. A release can complete no earlier than when the device thread reaches it, so the GPU tail is replaced 1:1 by device-thread lag.
  - So precise address-table store ranges (BDA write tracking) would gain at most ~0.2 ms here. Not built. The lever is the CPU per frame of the worker (~14 ms) and the device thread (~15.5 ms).
- **Kept** (neutral on Zorro, 22.30 vs 22.29 ms; they keep one thread's GPU wait from stalling the others):
  - **Timeline semaphore** (VK_KHR_timeline_semaphore): every CommandBatch signals its submission number on `Context::submitTimeline`.
  - **Worker reads**: a worker read finds the timeline value of the last batch writing its range (`DrawQueue::WriterTimeline`) under gpuMutex, waits for it without locks (`VulkanDevice::WaitTimeline`), then resolves.
  - **Completer**: it waits the same way for the label writers of ready releases.
  - `ANYPS5_NO_TIMELINE_WAITS=1` turns the timeline off.
- **Kept: queued flips.** Asynchronous flips are queued as a device-thread job behind the frame's draws instead of draining it (`ANYPS5_DRAIN_FLIPS=1` restores). `GpuReady` still runs from `finishCompletions`, never under gpuMutex: calling it in the job deadlocked `agc_driver_flip_tests`, whose `GpuReady` waits at a suspend point.
- **Tried and dropped:** a gpuMutex handoff letting worker resolves go before the device thread's next job (no effect; the long holder was the completer, not unfairness).

## GPU side (2026-10-12, Zorro gameplay)

- **Where the GPU time goes.** GPU busy 13.8 ms a frame, 13.5 of it draws and dispatches; copies are 0.3 and texture uploads ~0 (ANYPS5_GPU_TIMING). Per-draw profile (APS5_PROFILE_GPU_DRAWS, merging off, so shares only):
  - the 1080p G-buffer draws, hundreds at 17–21 µs each;
  - a 4096² shadow map at ~11 µs a draw;
  - one post-processing dispatch at 1.53 ms, of which 0.10 work, 0.69 setup and 0.75 teardown. It writes the display buffer (1920x1080, 4-byte texels, tile mode 4, the two flip buffers in turn) as a storage image: detile into a staging buffer, then copy the buffer to the image, and the reverse for write-back.
- **The upload's real cost.** Skipping the upload outright (unsafe experiment) cut the GPU tail from 4.01 to 3.14 ms and the frame from 22.09 to 21.27 ms.
- **Residency tried and dropped.** Keeping the image after write-back and reusing it when nothing wrote the range since (the texture cache's checks) adopted for a while, then never. In gameplay the UI is drawn over the display buffer after the pass, so guest memory really differs. Skipping the upload soundly needs proof that the shader overwrites every texel.
- **One-pass tiling (kept).** `TextureDetile.comp` built with `LINEAR_IMAGE` (`TEXTURE_DETILE_IMAGE_SPV`) reads and writes the image through an R32_UINT view (the image is created MUTABLE_FORMAT), with no staging buffer. It is used for 4-byte, single-layer 2D storage images on the GPU tiling path (`TextureDetiler::DispatchImage`); `ANYPS5_STORAGE_TWO_PASS=1` restores the old path. Results:
  - GPU tail 3.80 -> 3.48 ms;
  - A/B 60-88 s 23.45 -> 22.20 ms (one noisy round; realistically a few tenths of a millisecond);
  - device thread 15.52 -> 14.99 ms (no staging buffer created).

## Hellboy gameplay (2026-10-12, measured live: the user drives, hellboy_live.sh + live_sample.py)

- **Baseline.** ~85–90 ms frames.
  - Worker ~55 ms and device thread ~45 ms of CPU a frame (gperftools; glibc allocator for the profiler).
  - GPU busy ~48 ms: ~3,700 draws and dispatches a frame, the scene rendered at 3840x2160 into 1920x1080 display buffers. The game chooses that itself: default output mode, 1080p status, 1080p display buffers.
  - The chain is serial, like Zorro's: decode 68.7 ms + GPU tail 12.7 + 1.2.
- **Capture memo churn (fixed).**
  - The memo filled to 16,384 entries and cleared ~45 times per 10 s. Erasing the entries (destroying ResourceCaptures) cost the worker ~10% of its time.
  - Only ~1.5% of lookups hit: 730k "walks" per 10 s, a known program with new user data.
  - Dropped entries are now destroyed on the reaper (`CaptureMemo::SetRetire`).
  - Programs whose captures hit under 1 in 8 after 64 lookups stop storing entries, re-probed after 4,096 draws (`ANYPS5_CAPTURE_MEMO_ALWAYS=1` stores all). Clears fell to 5–6 per 10 s and hits rose ~13x (~150k per 10 s).
  - `APS5_TRACE_CAPTURE_MEMO=1` counts outcomes. Zorro is unchanged (22.45 vs 22.64 ms).
- **Captures waiting for the GPU (fixed).**
  - Read waits (`APS5_TRACE_READ_WAITS`, GPU waits now attributed by site) showed 0.5–1.1 s per 10 s at dispatch and draw captures.
  - `APS5_TRACE_WRITER_WAITS=1` showed they were 8-byte WRITE_DATA / DMA patches inside the 64-byte lines captures read, queued on the GPU just before the dispatch.
  - The worker predicts those dwords (`predictWrite`), so a capture line now overlays them while their write is still the last writer, and reads the rest directly (`Driver::predictedLine`). `ANYPS5_NO_PREDICTED_CAPTURE=1` waits; `APS5_VERIFY_PREDICTED_CAPTURE=1` re-reads and compares (8,000 lines in gameplay, 0 mismatches).
  - GPU waits at dispatch captures went from 500–740 to 3 ms per 10 s, and at draw captures from 700–1,070 to 160 ms. Decode went 68.7 -> 61.7 ms.
  - The wait moved to the device thread (draw captures waiting on its jobs, ~1.2 s per 10 s) and the GPU tail grew to 17 ms.
- **Left.** The device thread (~49 ms CPU a frame) and the GPU (~48 ms at 4K) now pace Hellboy.
- **Render scale, stage 1 (opt-in, `ANYPS5_RENDER_SCALE=0.5`).** Neither KytyPS5 nor shadPS4 has a way to lower a game's internal resolution.
  - KytyPS5 reports a 4K output unless param.json `attribute3 & 0x4` opts in to detection. Hellboy's 0x1004 does, and we report 1080p, as Kyty would. It still renders 3840x2160 by its own design.
  - True resolution scaling would remap pixel coordinates in shaders, copies, compute and write-back. Instead, pipelines of render passes larger than 1920x1080 shade 2x2 fragments (VK_KHR_fragment_shading_rate, pipeline rate, enabled only with the switch). Targets, coordinates and copies stay at the game's sizes.
  - Fragment shaders that write depth, stencil or the sample mask, run per sample or use interlock stay 1x1 (SPIR-V scan, `CoarseShadingAllowed`).
  - Hellboy gameplay, same area: GPU busy 48 -> 28 ms a frame, frames ~82 -> 62.5 ms; the user found it looked fine. The device thread (~41 ms CPU) and worker (~40 ms) now pace it.
- **Device thread, batches and dirty ranges (2026-10-12).**
  - **Flush attribution.** `APS5_TRACE_FLUSHES=1` attributes batch submissions to their caller. In Hellboy, ~19,730 of every 20,000 came from `SubmitMarker`: each of the ~80 submissions a frame completed with a marker that submitted the open batch, so batches averaged ~13 draws.
  - **Markers ride on the open batch.** With the pipelined driver and idle flush (`DrawQueue::DeferMarkers`), a marker now rides on the batch being recorded, or raises the last submitted batch's. A wait for it submits the open batch, and the idle flush submits it when the device thread runs out of jobs. `ANYPS5_FLUSH_MARKERS=1` submits per marker.
  - **Dirty ranges cached.** `RenderCache::DirtyRanges` (published after every device job) is recomputed only when `ResidentDirtyGeneration` moves, which is when a surface's dirty state flips or the entry set changes. `ANYPS5_NO_DIRTY_CACHE=1` walks every time; `APS5_VERIFY_DIRTY_CACHE=1` compares (Zorro 3.5M and Hellboy 1.5M cached answers, 0 stale).
  - **Hellboy (profile, render scale on), sampled ms a frame:**

    | SubmitMarker | 1.28 | 0.02 |
    | Submit | 1.23 | 0.34 |

- **Hellboy against KytyPS5 (2026-10-12, same area, user driving).**
  - **Measured:**

    | | Kyty | AnyPS5 (live sessions, glibc allocator) |
    |---|---|---|
    | Frame rate | 30 fps | — |
    | Driver CPU per frame | one GPU thread, ~25 ms | worker ~40-55 + device ~42-67 ms |

  - **Source comparison (/tmp/rr/KytyPS5):** Kyty walks the SRT per draw too. It records on one thread, uses push descriptors and a device-local buffer cache with a ≤16 KiB stream path for CPU-dirty constants, and writes release labels at record time. Its shaders are from the same family (same bounds checks); its float handling is no cheaper.
  - **VRAM mirror tested on Hellboy (opt-in `ANYPS5_GPU_MIRROR=1`):** GPU 48 -> 71 ms, because every mirrored read called DrawQueue::Begin and so ended the render pass (merging lost at 4K). Fixed: `ResolveRead` takes the queue and begins only when it copies. Ranges with a page written in the last 500 ms are read in place (`ANYPS5_MIRROR_DYNAMIC_MS`), so rewritten constants are not copied per draw.
  - **With both fixes:** GPU 46 ms (no mirror: 48) and PCIe receive halved at best, but the device thread rose to ~67 ms CPU. In-place PCIe reads are not what makes our GPU frame 2.5x Kyty's, and the mirror stays opt-in.
  - In these sessions Hellboy was CPU-bound: GPU busy 46 of 97 ms.
- **Per-draw diet, first pass (2026-10-12).**
  - **Allocator.** Zorro A/B, mimalloc (normal) against glibc (the profiler's): glibc costs +2.4 ms worker and +1.8 ms device a frame (~16%). Profiles therefore overstate allocation (operator new ~24% of the worker under glibc), and live Hellboy numbers with the profiler overstate CPU by about that much.
  - **Kept.** Error messages built before the check, every call: `readFloat` built a string per float register of every draw. DecodeState 1.99 -> 1.30 ms sampled a frame (Hellboy). Also kept, without a measurable effect: stack buffers in DecodeVertexStageInfo, and a reserved specialization list in Prepare.
  - **Reverted.** Packing ShaderMemory line reads into 2 KiB chunks: a draw reads few lines, so each draw allocated (and zero-filled) a whole chunk; ShaderMemory::read rose 5.6% -> 7.1%.
  - **What is left.** Remaining per-draw allocation is structural: each draw builds a RecompileResult with its own descriptor vectors (materializeResult + Populate + destruction ~7 ms sampled a frame on the worker). Zorro's content memo hits ~75%, but ~470k materializations per 10 s bypass it.
